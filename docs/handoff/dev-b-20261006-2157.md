# B5 CallResult ingest handoff — Dev B

## Changed
- Added loopback-only `POST /api/calls/ingest` accepting the existing Pydantic `CallResult` model. No dashboard session cookie is required for the local call producer.
- Persisted required call metadata and audit event before returning. Transcript, Russian summary and slots are Fernet-encrypted for recorded calls.
- Enforced FR-21 persistence for `no_record=true`: transcript and summary remain NULL; only `slots.callback_number`, when present, is retained in encrypted `slots_enc`; other slots are omitted.
- Made duplicate `call_id` submissions idempotent: the first request returns 201 and may notify; repeats return 200 and do not create duplicate audit events or notices.
- Invoked the B4 `Channel.notify()` only after successful commit, using a minimal `Notice` without free-form summary. Notification failure does not roll back the saved call.
- Added synthetic integration tests for contract validation, loopback restriction, encryption, no_record, duplicate handling, audit, commit-before-notify and notifier failure.
- Updated `docs/STATUS.md`: B5 and FR-07 checked; FR-08 remains open until a live Telegram notice is verified.

## Decisions and dependencies
- `contracts/call_result.schema.json` and `app/schemas.py` were not changed.
- The endpoint is restricted to loopback clients, matching the local Uvicorn binding; authentication via dashboard cookies is not used by the internal producer.
- The existing `CallRecord` model has no duration/metrics columns; optional `duration_s`, `stt_avg_conf`, `latency_ms_p50`, and handoff/VIP extras are not separately persisted. The required FR-07 content and fields represented by the current model are persisted.
- Dev A should POST the completed CallResult to `http://127.0.0.1:8000/api/calls/ingest` after call completion. The route returns 201 for a new ID and 200 for a duplicate.
